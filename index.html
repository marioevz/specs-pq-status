What a post-quantum account can do with today's specs

EIP-8141 frame transactions plus ethereum/EIPs#12616 let a hash-based leanSPHINCS key authorize Ethereum transactions. This page tracks what that combination makes possible, what it doesn't, and the open questions, each backed by an executable test where one exists.

What #12616 adds

EIP-8141 introduces frame transactions: a transaction is a list of frames, and the account itself, running its own code, approves who sends it and who pays. Signatures sit in a separate list that the protocol verifies before anything runs. Contracts can read who signed (the scheme and the signer) but not the signature bytes.

#12616 adds a fourth signature scheme to that list, leanSPHINCS: a stateless, hash-based signature over Keccak-256 whose security does not depend on the hardness of discrete logarithms, so a quantum computer does not break it. The other schemes are ECDSA over secp256k1 (today's Ethereum keys), P-256 (passkeys), and ARBITRARY, whose bytes the protocol passes to the account's code unverified.

Just as important is what #12616 leaves out. The built-in default code, which lets a codeless account send frame transactions, still accepts only ECDSA, and there is no precompile for verifying leanSPHINCS signatures in contracts. A leanSPHINCS key therefore only controls an account whose code checks it.

Spec details for implementers
  • Scheme numbering: ARBITRARY = 0x0, SECP256K1 = 0x1, P256 = 0x2, LEANSPHINCS = 0x3. New protocol-validated schemes append after the existing ones.
  • A LEANSPHINCS entry's signer must be exactly the 32-byte public key (any other length is an invalid frame). Its resolved signer is that key, so SIGPARAM(i, RESOLVED_SIGNER) returns the full key as one word, not an address: an account tells the cases apart by SIGPARAM(i, SCHEME).
  • The public key is the 16-byte root of the top tree followed by the 16-byte public parameter. Verification is the verify of EthLib's Cryptography/Sphincs module at 03b7e4dd; the spec calls it through py-lean-pq.
  • The raw signature bytes are not introspectable: SIGPARAM(i, SIGNATURE_LENGTH) and SIGDATACOPY halt for protocol-validated entries (test).
  • Invalid encodings and tampered signatures are covered by test_leansphincs_entry_validation.

An account's lifecycle

Getting an account: deploy it in the first transaction

A new user with only a leanSPHINCS key computes their address in advance. It is the CREATE2 address of a public factory and of wallet code that embeds their public key, so the address itself commits to the key. Anyone can send ETH to it. The account's first transaction then does two things in order: a deploy frame asks the factory to create the wallet at the account's own address, and a verify frame runs the wallet just created, which checks the leanSPHINCS signature and approves the transaction. If the address holds no ETH, a sponsor can approve payment instead.

Front-running is harmless. Anyone can call the factory first, but all they can deploy is the wallet the address commits to, which only the owner's key controls. Deploying it does bump the account's nonce to 1, so a first transaction already signed for nonce 0 becomes invalid and has to be signed again. Before deployment, taking over the address would require finding different wallet code with the same 160-bit address, a preimage search of about 2160 work, or 280 with Grover's algorithm.

Spec details for implementers
  • For this to be safe, the factory must not depend on who calls it, the owner must be fixed in the initcode (no initialize() call afterwards), and the wallet must have no way to change its owner that bypasses the key.
  • Whoever writes the wallet code could plant a backdoor through a 280 collision search on the address (classically). Users should rely on audited, widely used wallet code.
  • The test factory is a 23-byte CREATE2 forwarder in the pre-state (source). EIP-7997's canonical factory is not in the Bogota devnet yet.
  • Sponsored deployment: the deployment creates the sender account, so when the sponsor's APPROVE_PAYMENT increments the sender's nonce, it creates no account and needs no state gas. Without a deployment, approving payment for a nonexistent sender charges NEW_ACCOUNT state gas first (test_state_gas.py::test_approve_creates_sender).
  • The sender's nonce is incremented once per transaction, when payment is approved, so it protects the sender even when someone else pays. Every empty-msg signature commits to it through the canonical signature hash.
  • The keyed nonces of EIP-8250 on the devnet would let a transaction survive a front-run deployment, since deploying only bumps the account nonce. This is untested.

Keeping an existing address

Someone who already holds an ECDSA account can keep its address: they delegate it (EIP-7702) to a small contract that calls SETCODEFROM (EIP-8298) to copy a leanSPHINCS wallet's code into the account. The account then has real code rather than a delegation, so the old ECDSA key no longer authorizes frame transactions from it. This depends on EIP-8298, which the devnet includes, and the migration transaction is itself signed with ECDSA, so it has to happen while that key is still safe.

Why not EIP-7702 or a leanSPHINCS default code?
  • An EIP-7702 authorization is signed with ECDSA and names the authority by its recovered address, so a leanSPHINCS key can't produce one. EIP-8141 deliberately has no authorization list of its own.
  • A codeless account never runs code of its own, so it cannot call SETCODEFROM.
  • Accepting leanSPHINCS in the default code was considered and dropped: deploying in the first transaction already gives a key-only onboarding path without help from anyone, while a default-code account would have no upgrade path, since 7702 is ECDSA-only.

Interacting with contracts

Many applications ask the user to sign a message rather than send a transaction: permits, orders, sign-in. Contract wallets answer these through EIP-1271: the application calls the wallet's isValidSignature(hash, signature). For an ECDSA or P-256 wallet the wallet's code verifies the signature itself using a precompile. There is no such precompile for leanSPHINCS.

What works today is to put the signature in the transaction. A frame transaction can carry an extra leanSPHINCS entry that signs an explicit 32-byte digest instead of the transaction. The protocol verifies it like any other entry, and code running anywhere in that transaction can read who signed what. The wallet then answers isValidSignature by looking the entry up.

This covers on-chain settlement, where a contract checks the signature inside a transaction, provided whoever submits it uses a frame transaction. It does not cover checks made outside a transaction, such as an order book or sign-in backend calling isValidSignature through eth_call, or ERC-6492 checks before the wallet is deployed. There the call simply fails. Closing that gap needs a way to verify leanSPHINCS in the EVM, which is an open question.

Contracts that only accept ECDSA, for example by calling ecrecover or implementing EIP-2612 permit without EIP-1271, can't be used by any smart account, post-quantum or not. Fixing them is up to the applications; pq-chain-analysis measures how much value sits behind them.

Spec details for implementers
  • The wallet checks SIGPARAM(i, SCHEME) == LEANSPHINCS, SIGPARAM(i, RESOLVED_SIGNER) == owner_key, and SIGPARAM(i, MSG) == keccak256(address(this) ‖ hash), with i ABI-decoded from signature (source).
  • SIGPARAM works at any call depth within a frame transaction and halts outside one, so the wallet's call fails rather than returning a wrong answer.
  • The EIP's warning about approving transactions on explicit-msg signatures does not apply: isValidSignature attests to a hash and authorizes no frames. Replay protection for the hash itself is the application's responsibility, as with EIP-1271 today.
  • Every attestation consumes one of the key's 230 signatures.

Cost

The 12,600 gas for verifying a leanSPHINCS signature is small. Carrying it is not: its 7,740 bytes are priced as transaction data, and EIP-7976's data floor makes data-heavy transactions pay at least 64 gas per byte. For a simple transaction the floor is what's charged.

A frame transaction with one verify frame, one sender frame with no data, one signature entry, and nonce 1, computed with the spec's calculate_frame_transaction_intrinsic_cost on the branch above. EIP-8141's constants are provisional.

So a leanSPHINCS transaction costs about 25 times as much gas as an ECDSA one, and about 95% of its minimum pays for the signature bytes. Lowering that cost is a question of pricing the bytes differently or of aggregating signatures, not of making verification cheaper. The same arithmetic applies to any in-contract verifier, which has to receive the 7,740 bytes as call data.

Open questions

QuestionWhy it mattersOptions and state
Verifying leanSPHINCS in the EVM Needed for EIP-1271 checks outside a frame transaction (off-chain, before deployment) and for contracts that verify signatures on arbitrary messages. A precompile (the 7,740 bytes of input still cost far more than verification), an EVM verifier (feasible with Keccak-256, unmeasured), or accepting the gap. Not committed either way.
Signature size and pricing The data floor makes each transaction cost at least about 523k gas, and 7.7 kB per transaction weighs on bandwidth and block size. Aggregation (the EIP keeps signature bytes hidden from contracts so it stays possible), or a different price for signature bytes. Neither is specified.
Basis for the 12,600 gas price Verification cost has to be benchmarked across clients. Provisional, like EIP-8141's other constants.
Expiry frame before a deploy frame The EIP says a deploy frame must come first and also that an expiry frame may only come first and is skipped when matching. It is unclear whether [expiry, deploy, verify] is a valid mempool prefix. Needs clarification in the EIP.
Public mempool coverage New accounts depend on the deploy prefix propagating. Cases are drafted for the mempool test format (accepted and rejected deploy prefixes, gas caps per scheme, a front-run deploy that is valid on-chain but must be dropped). Not implemented.
Keyed nonces and front-running A front-run deployment forces a re-sign with the account nonce. EIP-8250 keyed nonces, on the devnet but not in EIP-8141's text, would avoid it. Untested.
Canonical factory and SETDELEGATE Wallets should deploy through a shared, well-known factory. EIP-7997 (factory) and EIP-7819 (SETDELEGATE) are not in the Bogota devnet yet.
Signature budget per key 230 signatures per key, every attestation included, with no protocol counter. A wallet and paymaster concern. Key rotation patterns are not specified.
Forward compatibility with EIP-8288 Later post-quantum schemes and signature changes should fit without breaking these accounts. Not yet assessed.
Applications that only accept ECDSA Post-quantum accounts can't use them at all. An application-level migration to EIP-1271, outside protocol scope.
